# ABL MCU Platform — Архитектурная конституция

> **Статус:** v1.1 (2025-08-28): добавлены D9 (модель пинов Board + App-overlay) и D10 (лицензионная политика).
> **Назначение:** нормативный документ платформы. Все ключевые архитектурные решения, правила зависимостей и структура репозитория фиксируются здесь. Код, противоречащий этому документу, считается дефектом.
> **Изменения:** любое изменение глобальных решений — через раздел «Журнал решений» (ADR-стиль): новая запись с обоснованием и датой; безмолвно «поправить в коде» нельзя.

---

## 1. Назначение платформы

Кроссплатформенный SDK на открытом ПО для сборки прошивок MCU на Linux: один и тот же исходный код приложения и драйверов собирается под STM32, ESP32, AVR и другие архитектуры без изменения бизнес-логики.

Целевой пример «всё работает»: каталог `src/` проекта `blink` собирается под STM32 (bare и FreeRTOS), ESP32 (FreeRTOS) и AVR (bare) без единого `#ifdef PLATFORM_*`.

## 2. Цели и не-цели

**Цели:**
- Максимально высокоуровневая бизнес-логика: приложение и драйверы не знают о железе.
- Универсальные драйверы (датчики, периферия, протоколы), переносимые между платформами.
- Простая первая сборка: `setup.sh` (зависимости) → `build.sh -p <platform>` (сборка) → `flash`.
- Модульность и масштабируемость: новый драйвер / новая плата / новый МК добавляются без правок чужого кода.
- Воспроизводимость: vendor-SDK и тулчейны закреплены версиями в манифесте.

**Не-цели (сознательно):**
- Не заменяем Zephyr/ESP-IDF/STM32Cube: их сильные стороны (экосистемы, драйверы, wifi/BT) используем как фундамент L0.
- Не строим полный Kconfig/DTS сейчас (см. D5).
- Не обещаем hard-realtime гарантий сверх того, что даёт выбранный рантайм.

## 3. Ключевые архитектурные решения (D1–D10)

| ID | Решение | Обоснование | Статус |
|---|---|---|---|
| **D1** | Подъём платформы (SoC/board bring-up: тактирование, startup, system, линкер) живёт **в репозитории платформы**; проекты — тонкие (`src/` + конфиг) | DRY: иначе тактирование/startup копируются в каждый проект; «новый проект» = выбор платы | ✅ Принято |
| **D2** | Платформа — **монорепо** `abl-mcu-platform` (hal, soc, boards, drivers, system, connect, tools); проекты — отдельные репозитории | Модульность = каталоги с контрактами, а не репо. Единая версия и CI. Разделить монорепо потом легко, слить репо — больно | ✅ Принято |
| **D3** | ESP32 — **обёртка над ESP-IDF**: `target/esp32/` в проекте — корень IDF-проекта; сборка через `idf.py` | Только так доступны wifi/BT и рабочая прошивка. Осознанно принимаем «второй build-мир» для ESP32 | ✅ Принято |
| **D4** | **Компонентная модель модулей** + жёсткие правила зависимостей (раздел 12) | Масштабируемость: новый драйвер = новый компонент, без правок чужих CMake-файлов | ✅ Принято |
| **D5** | YAML владеет **пинами и выбором SoC/board**; тактирование и линкер-скрипты — обычный C/`.ld` в `soc/` | Прагматичная граница «источника истины»; не строим полный Kconfig/DTS на старте | ✅ Принято |
| **D6** | Контракт **рантайма** (sleep/task/mutex/queue/timer) + бэкенды `bare` и `freertos` | FreeRTOS — основной рантайм для STM32/ESP32; bare — для AVR и лёгких STM32-проектов. Драйверы пишутся один раз под контракт | ✅ Принято |
| **D7** | Точка входа приложения — `abl_main()`; платформенные трaмполины `main` (STM32/AVR) и `app_main` (ESP32) | IDF требует `app_main`, startup — `main`; единый `src/` без `#ifdef` | ✅ Принято |
| **D8** | **Native (x86/POSIX)** — полноценный порт HAL + хост-тесты | CI и отладка драйверов без железа; дисциплинирует контракты | ✅ Принято |
| **D9** | **Board = физика платы** (распаянное железо + onboard-алиасы `led0`/`btn0`); **App = overlay использования пинов** (`use:` ссылки или свои пины); `product.id` — метаданные сборки | Одна плата — много проектов; «почти одинаковые» проекты = один код, разные конфиги; проверка конфликтов — внутри проекта | ✅ Принято |
| **D10** | **Лицензионная политика:** платформа MIT; в прошивку линкуются **только пермиссивные** компоненты (MIT/BSD/Apache); copyleft (GPL/LGPL) в ядре запрещён; `LICENSES.md` — инвентарь лицензий | Коммерческие закрытые проекты (включая свои протоколы) возможны; защита от случайного «заражения» GPL | ✅ Принято |
| **D11** | **Языковые конвенции:** комментарии в коде — на английском (новый код; существующие русские переводятся постепенно, без отдельной кампании); README — двуязычные (RU + EN), оформляются позже | Единый язык кода для внешних контрибьюторов; документация остаётся доступной на русском | ✅ Принято |

## 4. Принципы (правила, которые нельзя нарушать)

- **R1. Направление зависимостей — сверху вниз.** Приложение и драйверы не включают vendor-заголовки (ST HAL, ESP-IDF, avr-libc) и не знают о конкретной платформе.
- **R2. `#ifdef PLATFORM_*` разрешён только в:** `hal/src/*`, `runtime/*`, `soc/*`, `boards/*`, трaмполинах `target/esp32`. Всё, что выше (приложение, драйверы), — запрещено.
- **R3. `mcu.part` — единственный ключ** отображения «платформа → device define, startup, system, линкер, тактирование». Маппинг существует в одном месте (раздел 8), никаких дублей.
- **R4. Драйвер зависит от контракта шины** (SPI/I2C/UART как интерфейс), а не от периферийного блока или vendor-HAL.
- **R5. Драйверы неблокирующие** (конечные автоматы), если контракт не требует иного. Это условие работы и в суперлупе, и в FreeRTOS.
- **R6. Сгенерированный код самодостаточен:** включает только необходимые контракты; никогда не включает `app.h`.
- **R7. Каждый модуль — компонент** с явными публичными include и зависимостями. Запрещены «глобальные» include-пути и линковка «вручную» из чужих CMake.
- **R8. Задержки и синхронизация** в приложении/драйверах — только через контракты (hal/runtime), не напрямую через vendor API.
- **R9. На STM32+FreeRTOS `HAL_Delay` не используется** (конфликт SysTick); sleep идёт через контракт рантайма.
- **R10. Конфигурация железа — в платформе (`boards/`, `soc/`);** конфигурация приложения — в проекте (`config/app.yml`).
- **R11. Board описывает только физику** (распаянное железо + onboard-алиасы); использование пинов конкретным приложением — overlay проекта (D9). Проверка конфликтов — внутри проекта.
- **R12. В прошивку — только пермиссивные лицензии** (MIT/BSD/Apache); copyleft-код в ядре платформы запрещён (D10).

## 5. Топология репозиториев

```
┌─────────────────────────────────────────────────────────────┐
│  abl-mcu-platform        ← монорепо платформы (D2)          │
│  (переименован из abl-mcu-platform-core на Шаге 1 миграции) │
│  hal / soc / boards / drivers / system / connect / tools    │
└─────────────────────────────────────────────────────────────┘
        ▲  подключается по манифесту в lib/
┌─────────────────────────────────────────────────────────────┐
│  abl-mcu-project-*        ← тонкие проекты-приложения       │
│  src/ + config/app.yml + (для ESP32) target/esp32/          │
└─────────────────────────────────────────────────────────────┘
```

**Модель зависимостей:**
- Проект хранит вендорский/платформенный код в `lib/` (**gitignored**, наполняется `setup.sh -d` из манифеста).
- `lib/abl-mcu-platform` — закреплённый тег платформы (при разработке допустим «соседний» layout как dev-удобство).
- Manifest (`manifest.yml` в платформе, эволюция `prerequisites.yaml`) — единственное место, где зафиксированы версии vendor-SDK и тулчейнов.
- Порядок разрешения путей: явный env/CMake-кэш → `lib/` проекта → глобальное хранилище (`~/.local/share/abl-mcu-*`) → FetchContent (fallback для CI).

## 6. Слои и направление зависимостей

```
┌──────────────────────────────────────────────────────────────┐
│ L4  app/  (проекты)        бизнес-логика, только контракты    │
├──────────────────────────────────────────────────────────────┤
│ L3  drivers/               переносимые драйверы (R4, R5)      │
├──────────────────────────────────────────────────────────────┤
│ L2  hal/include/abl + runtime контракты   (интерфейсы)        │
├──────────────────────────────────────────────────────────────┤
│ L1  hal/src/{stm32,avr,esp32,native}     порты (реализации)   │
│     runtime/{bare,freertos}                                  │
├──────────────────────────────────────────────────────────────┤
│ L0  soc/ + vendor SDK     (ST HAL, ESP-IDF, avr-libc, CMSIS)  │
└──────────────────────────────────────────────────────────────┘
```

Стрелки зависимостей направлены **вниз**. L2 — это набор интерфейсов; L1 — их реализации под каждую платформу; L0 — фундамент, который поставляет vendor, а `soc/` делает из него «готовую платформу» (тактирование, startup, линкер).

## 8. Модель SoC, Board и App (D5, D9)

Три уровня: **SoC** (общее для семейства), **Board** (физика конкретной платы) и **App/Product** (использование платы конкретной прошивкой). Ключевое разделение (D9): плата описывает, **что распаяно**; приложение описывает, **что и куда оно подключает**.

**SoC-дефиниция** — каталог на каждый (семейство, вариант), ключ — `mcu.part`:

```
soc/stm32/f1/STM32F103x6/
├── device_define: STM32F103x6      # device define для vendor-HAL
├── startup_stm32f103x6.s
├── system_stm32f1xx.c
├── STM32F103X6_FLASH.ld
├── clock.c                         # параметризовано кварцем из board
└── hal_conf.h                      # stm32f1xx_hal_conf.h (владение SoC)
```

**Board-дефиниция** (YAML в `boards/`) — только физика платы: МК, кварц и **распаянное железо** с каноническими onboard-алиасами (`led0`, `btn0`, ...):

```yaml
# boards/bluepill_stm32f103.yml
board:
  name: bluepill-stm32f103
  mcu: { part: STM32F103C6T6 }      # единственный ключ → soc-дефиниция
  oscillator: { source: hse, freq_hz: 8000000 }
  frequencies: { hclk: 72000000, pclk1: 36000000, pclk2: 72000000 }
  onboard:                          # распаянное на плате — принадлежит плате
    led0:   { port: GPIOC, pin: 13, mode: output, state: low }   # бортовой LED
    btn0:   { port: GPIOA, pin: 0,  mode: input, pull: up }
    usart1: { tx: { port: GPIOA, pin: 9, af: 1 },
              rx: { port: GPIOA, pin: 10, af: 1 } }
```

**App-конфиг (overlay)** — YAML в проекте: выбор платы, **использование пинов**, фичи, параметры:

```yaml
# config/app.yml
product:
  id: blink-bluepill-pro             # метаданные сборки (имя артефакта, версия)
  board: bluepill-stm32f103
  runtime: bare
pins:                                # overlay: чем пользуется ИМЕННО этот проект
  status_led:  { use: led0 }         # ссылка на ресурс платы (не знает порт/пин)
  button:      { use: btn0 }
  ext_sensor:  { port: GPIOB, pin: 6 }   # собственная внешняя обвязка проекта
features: { enable_log: true }
params:  { blink_period_ms: 250 }    # параметры бизнес-логики
```

**Наследование и разрешение:** `SoC ← Board ← App`. Кодогенератор получает на вход board + overlay: ссылки `use:` разрешаются в конкретные пины; **конфликты проверяются внутри проекта** (два сигнала overlay на одном пине, ссылка на несуществующий ресурс платы, пин вне набора платы — ошибка конфигурации). Конфликты *между* проектами не проверяются и невозможны: MCU исполняет одну прошивку за раз.

**Следствия (масштабируемость):**
- Одна плата — N проектов: одна запись в `boards/`, у каждого проекта свой overlay.
- Новая плата на существующем SoC = один YAML в `boards/`; в проекте меняется строка `product.board`.
- Новый МК = soc-дефиниция + board-YAML. Никаких правок в 5 местах (R3).
- «Почти одинаковые» проекты = один код + несколько `config/*.yml` (разные `product.id`, фичи, параметры), собираются по отдельности; runtime-режимы в одной прошивке — это бизнес-логика приложения, а не платформы.

## 9. Конфигурация и кодогенерация

**Граница (D5):**
- YAML владеет: физика платы (`board`: распаянное железо + onboard-алиасы) и использование пинов приложением (`app`-overlay), кварц/частоты, фичи, выбор SoC/board.
- Обычный C/`.ld` в `soc/` владеет: тактирование (PLL и т.п.), линкер-скрипты, startup/system.

**Кодогенерация:**
- `templates/` — **единственный** источник шаблонов (`.jinja`); скрипты читают их, инлайн-дубли запрещены.
- Генерируется: `hardware_pins.h` (+ таблица GPIO-инициализации), `hardware_config.h` (частоты/фичи как defines).
- Генерация пинов объединяет board + app-overlay (D9): ссылки `use:` разрешаются в пины, конфликты проверяются внутри проекта (раздел 8).
- `gen_linker` исключается (линкеры — в `soc/`).
- Сгенерированные файлы самодостаточны (R6): включают только нужные контракты (`abl_gpio.h` и т.п.), никогда `app.h`.
- Один и тот же YAML и скрипты работают и в обычной CMake-сборке, и в IDF-обёртке (раздел 14).

## 10. HAL-контракты

Все контракты — заголовки `hal/include/abl/abl_*.h`. Общие правила:
- префикс `abl_` (защита от коллизий с vendor);
- функции возвращают `abl_status_t` (`ABL_STATUS_OK/ERROR/BUSY/TIMEOUT`);
- хэндлы — непрозрачные структуры; кодировка (порт/пин/номер) определена и документирована в контракте для каждой платформы;
- ISR-безопасные варианты — с суффиксом `_isr`;
- потокобезопасность — ровно та, что обещает бэкенд рантайма.

| Контракт | Статус | Замечания |
|---|---|---|
| `abl_gpio` | есть | доработать: прерывания (EXTI), AF-номер, скорость, open-drain/push-pull |
| `abl_delay` | есть | переработать точность: DWT (Cortex-M), `esp_rom_delay_us` (ESP32); не хардкодить тактовую частоту |
| `abl_time` (тик) | есть | `abl_time_init` + `abl_time_uptime_ms` (STM32 — HAL tick, ESP32 — esp_timer, AVR — Шаг 8) |
| `abl_uart` | план | контракт шины — в первую очередь |
| `abl_spi` | план | контракт шины — в первую очередь |
| `abl_i2c` | план | контракт шины — в первую очередь |
| `abl_adc`, `abl_pwm` | план | |
| `abl_critical` (ISR/атомарность) | план | нужен драйверам сразу |
| `abl_runtime` | есть (`bare`) | sleep/uptime/task/run; mutex/queue/timer и `freertos` — по мере потребителей (Шаг 9) |

## 11. Рантайм (D6)

Контракт `abl_runtime.h` покрывает: sleep (ms/us), task, mutex, semaphore, queue, software-таймер, critical section.

**Реализовано на Шаге 7:** `abl_sleep_ms/us`, `abl_uptime_ms`, `abl_task_create`, `abl_runtime_run` в бэкенде `bare`; выбор бэкенда — `product.runtime` в app-конфиге проекта. mutex/semaphore/queue/timer и critical sections добавляются вместе с первыми потребителями; `freertos`-бэкенд — Шаг 9 (см. `runtime/src/freertos/README.md`).

| Примитив | `bare` (суперлуп) | `freertos` |
|---|---|---|
| `sleep_ms/us` | busy/systick | `vTaskDelay` |
| `task_create` | регистрация функции суперлупа (кооперативно) | `xTaskCreate` |
| `mutex` | no-op | `xSemaphoreCreateMutex` |
| `queue` | no-op/флаг | `xQueueSend/Receive` (+`_isr`) |
| `timer` | callback из тика | `xTimerCreate` |
| `critical` | `cli/sei` | `taskENTER_CRITICAL` |

**Обязательные условия:**
- R9: на STM32+FreeRTOS `HAL_Delay` запрещён; SysTick принадлежит FreeRTOS (настройка tick/`HAL_InitTick` — в soc-дефиниции).
- AVR — только кооперативный режим; драйверы неблокирующие (R5).
- Выбор бэкенда — через конфиг приложения (`app.yml`): `runtime: bare | freertos`.

## 12. Компонентная модель и драйверы (D4)

**Правила:**
- Каждый модуль (порт, SoC, board, драйвер, системный модуль) — компонент: каталог с собственным `CMakeLists.txt`, определяющий публичные include, приватные include, зависимости, defines.
- Публичный include-путь — только `include/` компонента; наружу виден минимум.
- Зависимости объявляются явно; циклы запрещены; единая функция регистрации `abl_component(...)` в ядре вместо ручных `target_include_directories`/`target_link_libraries`, разбросанных по чужим CMake.
- Vendor-SDK подключается **только** портами L1 и `soc/`.

**Паттерн драйвера:** драйвер получает «шину» — интерфейс с указателями на функции (`transfer`, `read/write`, `sleep`, `gpio` для CS/RESET/IRQ), реализуемый портом платформы. Один и тот же исходник драйвера работает на STM32/ESP32/AVR и тестируется на host с моком шины.

## 13. Точка входа и жизненный цикл приложения (D7)

- Переносимый код: `src/main.c` определяет `void abl_main(void)` — вызывает `abl_target_init()` (из `soc/`), затем бизнес-логику (суперлуп и т.п.).
- Трaмполины (только они знают о платформе):
  - STM32/AVR: `int main(void)` — в `soc/` (startup вызывает `main`).
  - ESP32: `void app_main(void)` — в `target/esp32/main/main.c` (IDF вызывает `app_main`).
- Инициализация GPIO из YAML — сгенерированная функция, вызываемая `abl_target_init()`.

## 14. ESP32-стратегия (D3)

**Layout обёртки в проекте:**

```
abl-mcu-project-blink/
├── src/main.c                  ← общий код (abl_main)
├── CMakeLists.txt              ← обычная сборка (STM32/AVR)
└── target/esp32/               ← корень IDF-проекта
    ├── CMakeLists.txt          ← project(...), EXTRA_COMPONENT_DIRS
    ├── sdkconfig.defaults
    └── main/
        ├── CMakeLists.txt      ← регистрация общих исходников
        └── main.c              ← app_main() → abl_main()
```

**Механика:**
- IDF-конвенция «main/main.c в корне проекта» переносится в подкаталог `target/esp32/`; конфликта двух build-систем в одном корне нет.
- Общие исходники подключаются как дополнительный компонент через `EXTRA_COMPONENT_DIRS` (обход ограничения IDF на `SRCS` вне каталога компонента); `main/` — тонкий трaмполин.
- Кодогенерация из YAML — те же скрипты, вызываемые из IDF-CMake; сгенерированный include-путь добавляется компоненту.
- `sdkconfig`/partition table — внутри обёртки, gitignored.
- Сборка/прошивка/монитор: `idf.py -C target/esp32 build|flash|monitor` (IDF v5.2.2, `IDF_PATH` готовит `setup.sh`).

## 15. Инструментарий, сборка, отладка

- **CMake** (≥3.20) + **Ninja**; вход — `build.sh` (дискавери конфига) и CMakePresets (dev-удобство; пресеты обязаны передавать все требуемые переменные, иначе считаются дефектом).
- **Тулчейны:** `arm-none-eabi-gcc` ≥12 (STM32), `avr-gcc` ≥5 (AVR), ESP-IDF v5.2.2 (ESP32), системный компилятор хоста (native).
- **Установка:** `setup.sh` по `manifest.yml`: общие зависимости, тулчейны, SDK; `--check-only`; Python-пакеты в venv (не глобально).
- **Отладка/прошивка:** STM32 — OpenOCD + GDB (конфиги — часть board/soc-дефиниций), AVR — avrdude + simavr, ESP32 — `idf.py`.
- **Воспроизводимость:** Docker-образ с тулчейнами (план).

## 16. Тестирование (D8)

- **Native-порт** `hal/src/native/`: gpio = мок/файл, time = `clock_gettime`, uart = pipe/pty. Это четвёртый бэкенд HAL, равноценный остальным.
- Хост-тесты драйверов на моках шин в `tests/` — гоняются мгновенно, без железа.
- CI (план): матрица «все платформы собираются» + native-тесты.
- Критерий качества контракта: «то, что нельзя сымитировать на native, скорее всего, спроектировано неправильно».

В прошивку линкуются **только пермиссивные** компоненты: STM32 HAL (BSD-3-Clause), CMSIS (Apache-2.0), ESP-IDF (Apache-2.0 + бинарные блобы wifi/BT Espressif — стандарт отрасли для коммерческих продуктов), FreeRTOS (MIT), avr-libc (BSD).
